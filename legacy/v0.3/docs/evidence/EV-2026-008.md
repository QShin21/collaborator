Windows 常规单测 414 项通过（7 项跳过），`tk,win32,uia` 必需自检通过。
单独的原生替身窗口 8 项中 7 项通过；粘贴用例仍报 `not_received`，剪贴板正文和 locale 复原成功。

失败后的脱敏诊断显示：草稿长度为 29，等于替身原文长度 20 加欲贴文本长度 9；
目标窗口一直是前台，UI Automation 焦点、目标线程 GUI 焦点及原生编辑框焦点都匹配。
这强烈支持「Ctrl+V 到了正确编辑框，但 Ctrl+A 没有完成全选」；长度与焦点事实本身不等于键盘消息逐条证明。
微软的 [WinForms TextBox.ProcessCmdKey 文档](https://learn.microsoft.com/en-us/dotnet/api/system.windows.forms.textbox.processcmdkey?view=netframework-4.8)
明确说明：较旧的 .NET 兼容行为下，启用快捷键的多行 `TextBox` 对 Ctrl+A 不全选；
设 `Switch.System.Windows.Forms.DoNotSupportSelectAllShortcutInMultilineTextBox=false` 可启用新行为。

本地随后只在 PowerShell **替身进程**创建控件前设该开关，保留多行原生框、真实 Ctrl+A/Ctrl+V、
产品代码及严格失败断言；增加独立前置契约检查，先折叠选区，注入 Ctrl+A 后验证全选且正文未变，
再折叠并读回确认，避免替身预选状态使后续粘贴假通过。
若旧行为仍存在，契约测试与粘贴测试应继续失败。该调整尚待 Windows 重跑；
即使替身通过，也不等于真实 Codex 的非空中文/多行草稿替换通过。

工作流整体显示 success，是因为替身测试步骤是 informational。真实 Codex 未运行；M0-03 仍未完成。
