# 伴行 · 你先走，我陪着

**Problem-solving of authentic challenges** —— 帮助人们用 AI 解决真实世界问题的协作者。

很多人用不好 Codex，不是因为它不够强，而是因为真实的想法往往是**结构不良**的：「想在阳台做一个三层的花架，我没做过木工。」
这句话可以直接发出去，但换三种问法，拿到的第一份成果会完全不同。

伴行（Banxing）是一个待在 Windows 版 Codex 窗口旁边的小伙伴。你照常在 Codex 里打字，把想做的事写下来，停一下：

```
三条路线 · 选一条填入 Codex

主线  先做纸样比一比    拿到能打印的等大纸样      预览
      因为：没做过木工，先确认尺寸放得下最省事
支线  先做单层练手      拿到单层的图纸和材料单    预览
支线  买现成的来改      拿到改装步骤和采购清单    预览

依据：草稿                                      换一批
```

选一条，提示词就填进输入框——**你的原话一个字不改，放在最前面**，后面接上这条路线要 Codex 做什么、交什么、怎么检查。
问题始终由你提出；选哪条、改不改、发不发，也都由你决定。伴行从不替你发送。

随着你越写越清楚，伴行会越说越少：

| 档位 | 伴行做什么 |
| --- | --- |
| **带路** | 每份草稿给三条路线，其中一条标为主线并说明理由 |
| **提点** | 只指出这份草稿还缺什么；点一下，在草稿**末尾**补上一句 |
| **同行** | 只在说得出「这次出声能解决哪个具体问题」时才出现 |

草稿已经可以直接发时，哪一档都不出气泡。连着忽略会自动降一档（可以一键改回）；草稿经常可以直接发时，伴行会**问**你要不要少说一点；
升档只由你自己在菜单里决定。

> **当前状态（v0.3.0，二代首发范围）**
> - 产品规则、界面、校准与证据工具：**离线通过（E1）**——Linux 上的自动化测试，合成输入、内存里的模拟 Codex、离线替身模型。
> - Windows：**运行器替身检查通过（E2）**。416 项单测（8 项跳过）、必需自检和单独 9 项原生窗口检查通过，
>   包括真实 Ctrl+A 全选、粘贴替换及剪贴板正文/locale 复原。它不是 Codex。打包与发布工作流尚待运行。
> - 真实 Codex 窗口上的读稿、回填、输入法、焦点、认聊天：**E0，未验证**。
> - 真实模型给出的路线质量：**E0，未评估**（替身模型只说明流程走得通）。
>
> 因此伴行在一台机器上**通过校准之前，不会自动读取或填写 Codex**。证据等级的含义和逐项台账见
> [`docs/verification.md`](docs/verification.md)，真机验收步骤见 [`docs/acceptance.md`](docs/acceptance.md)，
> 已实现与未实现的清单见 [`docs/banxing-generation2.md`](docs/banxing-generation2.md) 开头的「实施状态」。

## 安装（Windows）

1. 到 [Releases](https://github.com/QShin21/collaborator/releases) 下载 `Banxing-<版本>-windows-x64.zip`，解压。
2. 双击 `Banxing.exe`。程序未签名，SmartScreen 提示时选「更多信息 → 仍要运行」。
3. 首次启动会打开「模型配置」：选择模型服务、填 API Key。窗口里写明草稿会发往哪个地址，点「同意并开启跟随」。
4. 打开 Codex，右键伴行 → 「校准（开启自动跟随）」，照着做九个小动作（约三分钟）。校准只用固定的测试短语，不保存你写的任何文字。
5. 校准通过后，在 Codex 输入框里写下想做的事，停一下。

不想马上配置模型或校准？右键伴行 → 「内置示例」可以先看两组完整的路线；「粘贴草稿」可以对任意一段文字要三条路线并复制。

## 怎么用

| 你做什么 | 伴行做什么 |
| --- | --- |
| 在 Codex 里写草稿，然后停大约 1.5 秒 | 读取草稿（以及这个聊天最近三轮里相关的片段），请求模型，按当前档位出气泡或保持安静 |
| 继续打字、用输入法选词、输入框为空 | 保持待机 |
| 点气泡里的一条路线 | 核对聊天、输入框、草稿都没变，然后把「原话 + 这条路线」写进输入框。不会替你发送 |
| 点行尾「预览」 | 分段显示：哪些是你的原话，哪些是加上去的；可「填入 Codex」或「复制」 |
| 点「换一批」 | 同一份草稿再要三条不同的路线（每条消息一次） |
| 提点档下点一条提醒 | 在草稿末尾补上那一句；气泡留着，可以接着补；菜单里可恢复成最初的原话 |
| 路线里涉及删除、提权之类的操作 | 这一条不会一点就填：先展开预览并标出提醒，由你在预览里确认 |
| 继续编辑、发送、切换聊天或应用 | 收起气泡。同一份草稿只提示一次 |
| 草稿发出去了，路线才回来 | 不打扰；十分钟内点一下伴行，可以看「刚才那句还可以这样问」 |
| 点一下伴行 | 现在就给当前草稿三条路线（任何档位下都可以） |
| 右键伴行 | 陪伴方式、暂停、是否参考当前聊天、重试、恢复原草稿、关于我、粘贴草稿、内置示例、模型配置、校准、兼容性自检、导出证据包、清除本机数据 |

**关于我**：可以写几句长期有效的情况（「我没有编程基础」「家里没有电钻」），它们会随每次请求发给模型。伴行还会在本机记住你常选哪一类路线，
用来排主线；可以随时清零。

## 隐私与安全

- 草稿只在你停顿时发送给**你自己配置的**模型服务；聊天片段是可选的，只取这个聊天最近三轮里和草稿有关的部分。气泡底部写明这次依据了什么、遮盖了几处疑似密钥。
- 首次开启时窗口里写明草稿发往的地址（协议、主机、端口），同意只对这个地址有效；地址一变就要重新确认。
- API Key 用 Windows DPAPI 加密保存（加密失败就不保存，绝不改存明文），并绑定到输入它时的服务和接口地址：更换地址（包括用环境变量覆盖）必须重新提供 Key。
- 只发往配置的地址：模型服务返回的跳转（重定向）一律不跟随；请求失败不会在后台改写后重发。模型连续失败三次后暂停自动请求，点「重试」恢复。
- 模型的回复在显示前要过一道安全闸：出现草稿和聊天里都没有的网址、把内容发到别处、下载后直接执行、要求忽略先前指示之类的内容，整批不显示。
- 未校准不跟随、不回填；密码框不读；只读 Codex 的输入框和本机会话记录，只写这一个输入框，从不按回车。
- 采用 / 忽略统计、档位和试用记录只保存在本机（`%APPDATA%\Banxing`），不含草稿和聊天内容；「关于我」加密保存在本机。
  菜单「清除本机数据」一键全部删除。路书（一段任务的过程记录）本版没有实现，也不保存。
- 「导出证据包」生成的文件只有是/否、数量、耗时、控件类型和文字**长度**，保存前全文显示给你看；伴行不上传任何东西。

## 读不到 Codex 时

右键伴行 → 「校准」，结果页会说明哪些能力开了、哪些没开。需要开发者帮忙时用「导出证据包」把结果保存成文件发过去（不含草稿和聊天内容）。
「兼容性自检」给出更细的一份文字报告。在此期间可以用「粘贴草稿」得到三条路线并复制。

## 从源码运行

需要 Python 3.9+（带 tkinter）。核心只用标准库；Windows 上读写 Codex 窗口需要 `comtypes`，托盘图标需要 `pystray` 和 `Pillow`。

```
pip install -r requirements-windows.txt      # 仅 Windows
python run.py                                # 启动伴行（Windows 上也可双击 start.bat）
python run.py --demo "想做个记账的小工具，每天记几笔花销，月底能看汇总"
python run.py --demo "想做一个放在玄关的换鞋凳" --mode hint
python run.py --eval                         # 评测场景的结构检查（60 个场景）
python run.py --selftest                     # 自检
python run.py --probe --fill                 # 兼容性报告（切到 Codex 窗口）
python run.py --summary                      # 本机试用记录汇总（含来得及率、可直接发送率）
python -m unittest discover -s tests -v      # 测试
```

没有模型密钥时，设置环境变量 `BANXING_PROVIDER=mock` 可用离线替身模型体验流程（固定模板，**不代表路线质量**；用它跑的评测报告会自动标为「仅流程」）。
`--demo` 用真实模型时同样需要先同意发送地址：在「模型配置」里确认过，或加上 `--agree https://实际地址`。
`--eval` 只在已经同意过这个地址之后才会发送场景。
其他环境变量见 [`.env.example`](.env.example)。

## 发布新版本

1. 修改 `banxing/__init__.py` 里的 `__version__`，更新 `docs/verification.md` 的台账。
2. `git tag v0.3.0 && git push origin v0.3.0`（或在 Actions 页面手动运行 `release` 并填版本号）。
3. GitHub Actions 在 Windows 上跑测试、原生替身回填检查、用 PyInstaller 打包、对打包结果运行自检，然后把 zip 发布为预览（pre-release）。
   替身检查失败会阻止发布。
   工作流全绿只说明到 E2；发布说明里不得写成真机通过。

## 来历

项目发起人最初的设想（原话）：

> 制作一个帮助人们使用ai解决真实世界问题的的ai-collaborator，**problem-solving of authentic challenges。**
>
> 学生行动：学生主动描述问题、提出问题、提出目标、提出即使是模糊的想法，即结构良好问题或者结构不良问题，作为agent的大前提；学生探索问题的具体任务、解决问题等。
>
> AI行动：1.读取并理解结构良好问题或提供脚手架解决结构不良到良好的gap（实现原理：提供广度的知识，提供有可能的一些脉络，主线支线，然后给人选择）；
> 2.在读屏之类的基础上，提供冒泡式的idea，具有启发性、建议性，一定时长后冒泡淡化，或人主观地参考冒泡idea进行深入讨论与学习；人的反馈可以调整agent的能动性和偏好，接受、忽略、扩展讨论都会对agent进行调整
>
> 改造前后的对照：用不同的agent，前后测与横评。

v0.1.0 把它做成了本地 Web 工作台（见 tag `v0.1.0`，代码存档在 `legacy/v0.1/`）。一代（0.2，未发布）按发起人新的产品方案
（原文只在本地保留，不随仓库发布）收敛为面向 Windows Codex 的开工桌宠，设计存档见 [`docs/product-design.md`](docs/product-design.md)。
二代更名为伴行：学生先行动（写草稿），AI 提供几条脉络、分出主线支线给人选择，以冒泡的形式出现，并根据接受与忽略调整自己的主动程度——
目标是脚手架能一点点撤掉。
